## Post

Do you actually know why you added that liveness probe?

I run self-hosted apps on Kubernetes. Audiobookshelf, Linkding, Grafana. Apps I didn't write, so I can't just add a health endpoint whenever I want. I have to work with whatever the app exposes.

Before I configure any probe, I ask four questions:

1. Can the app break while the process is still running? If yes, you need a liveness probe. A crashed database connection, a deadlocked thread, a corrupted file — the process stays alive but the app is dead. Kubernetes won't know without a probe.

2. Does it receive traffic and need time to become ready? If yes, you need a readiness probe. Without it, requests hit the pod before it's ready to handle them.

3. Does it start slowly? If yes, you need a startup probe. It buys the app time to initialise without the liveness probe killing it first.

4. Is it managed by an operator? If yes, the operator likely handles health checking already. Check before adding your own.

For both of my apps the answers were: yes, yes, no, no.

Liveness probe. Readiness probe. No startup probe.

Two questions, two probes, one clear decision. No guessing.

What's your process for deciding which probes to configure?
