# Cloudlab: A Multi-Tenant Platform on Azure Kubernetes

## The Goal

Build a platform where every customer gets their own isolated app, database, and backups, running on Azure Kubernetes, provisioned by Terraform, and kept in sync automatically by Flux. Adding a new customer should be a one-line change.

That's the whole brief. Everything below is how I built toward it.

## The Components, Whiteboard-Level

Before the detail, here's the map.

**Terraform** provisions the Azure side and generates every customer's Kubernetes manifests. **AKS** is the cluster itself, one system node pool for critical add-ons and one user pool for everything else. **Flux** is the GitOps controller inside the cluster — it polls this repo every five minutes and applies whatever it finds. **Kustomize** is what Flux uses under the hood to compose those manifests. **Azure Key Vault** holds every password and token; nothing sensitive lives in Git. **CloudNative-PG** runs Postgres — each customer gets their own dedicated database, not a shared one, backed by the **Barman Cloud plugin** streaming backups to Blob storage. **Traefik** routes traffic in, **cert-manager** issues the TLS certificates automatically, **Cilium** enforces network isolation between customers. And **n8n** is the actual application every customer runs.

That's the whole stack. Now the parts worth explaining properly.

## How Kubernetes Manifests Get Written

Terraform doesn't apply anything to the cluster. It writes plain YAML files to the repo, and Flux is the only thing that ever touches Kubernetes.

The mechanism is a Terraform `local_file` resource — Terraform writing files to disk, the same way you'd write a config file by hand, except it interpolates variables into a template first:

```hcl
resource "local_file" "namespace" {
  filename = "${local.customer_path}/namespace.yaml"
  content  = <<-YAML
    apiVersion: v1
    kind: Namespace
    metadata:
      name: ${var.customer_name}
      labels:
        pod-security.kubernetes.io/enforce: restricted
  YAML
}
```

That pattern repeats thirteen times per customer — namespace, secrets, config, database, backup target, backup schedule, deployment, service, ingress, network policy, monitoring, storage, and the file that ties them together. One customer, thirteen files, all plain readable YAML.

> **[INSERT DIAGRAM: one customer name → thirteen manifest files]**

The point of writing files instead of templating them is that nothing is hidden. Every customer's config sits in Git exactly as it will be applied — no one has to mentally expand a template to know what's actually running.

## The Cloud Resources

The same fan-out drives the Azure side. One block in Terraform:

```hcl
module "customer" {
  source   = "../modules/customer-onboarding"
  for_each = local.customers
  customer_name = each.key
  ...
}
```

`local.customers` is a plain list — right now, three names. `for_each` runs the module once per name. Each run creates a private Blob storage container for that customer's backups, a SAS token scoped to only that container, a generated database password, and five secrets in Key Vault (database credentials, the backup token, and Telegram alert routing).

None of that is shared. What is shared, created once regardless of how many customers exist, is the AKS cluster itself, both node pools, the Flux extension, the Key Vault, and the storage account those containers live inside.

> **[INSERT DIAGRAM: shared infrastructure vs per-customer resources]**

Three customers today means three containers and fifteen secrets sitting inside one vault. A fourth customer means one more name in the list.

## How Secrets and Passwords Are Handled

Nothing sensitive is ever committed to Git, not even encrypted. The path is: Terraform writes the actual secret value into Key Vault, and the only thing that lands in the GitOps repo is a *reference* to that secret's name.

Inside the cluster, a `SecretProviderClass` tells the Secrets Store CSI driver which vault, which identity, and which named secrets to pull:

```yaml
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: luffy-secrets
spec:
  provider: azure
  parameters:
    keyvaultName: "kv-cloudlab-prod"
    objects: |
      array:
        - objectName: luffy-db-password
          objectType: secret
  secretObjects:
    - secretName: luffy-db-credentials
      type: kubernetes.io/basic-auth
```

The pod mounts that as a CSI volume, and the CSI driver mirrors the values into a native Kubernetes `Secret` the pod can consume normally through `envFrom`. The identity doing the reading is AKS's own Key Vault Secrets Provider add-on, granted `Key Vault Secrets User` on the vault and nothing more.

## Built for Easy Onboarding

Adding a customer is meant to be this:

```bash
vim staging/customers.tf   # add one name to the list
terraform apply            # creates cloud resources, generates manifests
git push                   # Flux picks it up within 5 minutes
```

That's only possible because the fan-out described above — cloud resources and Kubernetes manifests — is driven by the same single list. One name added, one `terraform apply`, and both sides come up together. Every customer gets an identical setup, and nobody writes that config by hand.

## Monitoring and Alerting

Every customer's database is scraped automatically. The same Terraform module that generates a customer's manifests also generates a `PodMonitor` — the resource that tells Prometheus which pods to collect metrics from. A new customer shows up in monitoring without anyone configuring it.

On top of Prometheus sits Grafana with 14 alert rules covering the things that actually matter: failed backups, WAL archiving breaking, replication lag, nodes going unready, disks filling up, and the customer app itself not running. When a rule fires or resolves, the alert lands in Telegram.

One deliberate choice here: Alertmanager — the component that usually handles alert routing in this stack — is turned off. Grafana's own alerting does the job instead, and the alert rules live as plain YAML in Git like everything else, so Flux deploys and versions them the same way it does the apps. One less component to run, and the alerts are code-reviewed like any other change.

The result is that a phone buzz, not a dashboard check, is how I find out something's wrong.

## Built for Resiliency, and What That Led To

The design called for three database replicas per customer — proper high availability, not a single point of failure. That's CNPG's default in this module, and it's what real production usage should run.

Testing three customers at once is what exposed the limit.

Three customers × three replicas + one app volume each is twelve disks. Azure caps how many disks a node can attach, and on a three-node pool, twelve is the ceiling. Prometheus asked for its own volume and there was nowhere to put it.

The obvious fix was a fourth node. Azure said no — the subscription's vCPU quota was already spent.

So replicas came down from three to one for this demo environment, and the running databases had to be patched directly, since a StatefulSet doesn't shrink itself just because the desired count in Git changed.

That's the honest state of it: the design targets three replicas, the demo runs one, and the fix for production is a quota increase, not a redesign.

## Troubleshooting

A few things broke along the way. Worth walking through, since each one taught something specific.

**Traefik silently served the wrong certificate.** The chart's default ingress class was named `traefik-traefik`; every generated ingress asked for plain `traefik`. Nothing matched, so Traefik fell back to its own self-signed cert on every customer's domain. Found with `kubectl get ingressclass`, fixed by naming the class explicitly instead of trusting the chart default.

**Two Helm releases silently failed to install.** Both the Traefik chart and the CNPG backup plugin were pinned to open-ended version ranges (`"33.x"`, `"0.x"`) that aren't valid semver. Flux doesn't error on that — it just never reconciles, and the failure looks identical to "nothing's wrong yet." Pinning both to exact versions fixed it.

**A HelmRelease was watched by nobody.** Flux only reads Helm resources from the `flux-system` namespace. One release had `metadata.namespace: cnpg-system` — the namespace it deploys *to*, not the one Flux reads *from* — so it was invisible until that one field was corrected.

**The Key Vault identity kept going stale.** Every AKS cluster rebuild issues a new managed identity, and every `SecretProviderClass` that hardcodes the old one breaks. This happened three separate times across the project. I added a Terraform output that prints the current identity as a rebuild reminder — the manual step itself is still there, and it's the next thing to automate away.

## Where It Stands

The repo reproduces the whole thing from nothing — clone it, run `terraform apply` against a subscription, and the cluster, databases, and customers come back exactly as defined. Nothing runs 24/7; it's provisioned on demand and torn down between demos, because there's no reason to pay for idle AKS nodes.

The gap between what's designed (three replicas) and what's demonstrated (one) is the most honest thing about this project, and it's also the most useful lesson: cloud constraints are architecture constraints, and the fix for a demo limitation is knowing exactly which knob to turn when it's time to run for real.
