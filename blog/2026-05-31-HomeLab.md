# I Built a Kubernetes Home Lab on Raspberry Pis. Here's The Entire Stack.

Everything I learned deploying Mealie to Rancher Desktop stayed theoretical until I took it off my laptop.

That's when I built the home lab.

Two Raspberry Pis, a QNAP NAS, a lot of trial and error, and enough late nights debugging why persistent volumes weren't mounting to fill a small blog. This isn't a polished enterprise setup. It's a working Kubernetes cluster running real applications, managed entirely through Git, with zero open ports on my router.

What shocked me was how much of what works in a home lab directly maps to how enterprise teams run Kubernetes. The architecture isn't different. The scale is.

---

## The Hardware: Two Pis Named After One Piece

Pi Zoro is the control plane node. Pi Luffy is the worker.

Naming matters more than it sounds. When you're troubleshooting at midnight across multiple nodes, memorable names stick. Forgettable names blur together.

Both run Arch Linux on 16GB RAM Raspberry Pi 5s with Waveshare PoE HAT Type F modules. That means they get power and network connectivity over a single ethernet cable, which keeps the setup clean and eliminates power adapter clutter.

The Netgear GS308EPP is a managed PoE switch that powers both Pis and connects everything together — the cluster, the NAS, any other network devices. It's not fancy, but it's reliable and lets me do everything over ethernet. The hardware is solid for a home lab. K3S is lightweight enough that it runs fine, leaving plenty of headroom for applications and monitoring. The real storage doesn't come from the Pis — it comes from the QNAP NAS. That was the decision that mattered most.

---

## K3S: Kubernetes That Actually Fits

K3S installs with one command. It's Kubernetes stripped down to the essentials, runs on a Raspberry Pi, and lets you SSH in and troubleshoot at the OS level. Rancher uses K3S in production. That fact matters. Everything I build here isn't just a toy cluster. It's production-relevant.

The install is straightforward:

```bash
curl -sfL https://get.k3s.io | sh -
```

The control plane runs on Zoro. The worker runs on Luffy. They find each other through a shared token. By the time the install finished, I had a functional Kubernetes cluster.

Now I had to decide what to do with it.

## How Everything Works Together

A Kubernetes cluster without the right operational backbone is just expensive electricity. I needed pieces that would teach me how teams actually run infrastructure at scale.

**GitHub is the single source of truth.** Every resource definition lives there — deployments, services, secrets, configurations, everything. This isn't just for backups. It's the contract that defines what the cluster should be.

**Flux watches that repo.** When you push a change to Git, Flux sees it and applies the change to the cluster. No manual kubectl applies. No guessing about what changed. The cluster becomes a reflection of Git.

**Renovate extends that idea to container images.** When a new image is available, Renovate opens a pull request with the updated version. You review it, merge it, and Flux automatically redeploys with the new image. Updates flow through the same Git pipeline as everything else.

**SOPS keeps secrets safe inside that same Git repo.** Instead of storing sensitive data as plaintext, SOPS encrypts only the sensitive fields. The encrypted YAML stays committed. Only the private key (stored as a Kubernetes secret inside the cluster) can decrypt it. Change a secret, push to Git, Flux applies it, everything stays auditable.

On the hardware side, the control plane (Zoro) runs infrastructure: Prometheus collects metrics, Grafana visualizes them, Traefik routes external traffic, Linkling runs the bookmark service. The worker node (Luffy) runs application workloads: Audiobookshelf serves audiobooks and podcasts, Alertmanager handles alerting, democratic-csi manages storage requests.

**Storage is divided by need.** The QNAP NAS provides two backends via democratic-csi. iSCSI LUNs give raw block storage for high-performance needs and configuration data that needs reliability. NFS shares give file storage for audiobooks, podcasts, and other data accessed like regular files. Any pod can request persistent storage and get routed to the right backend.

**Access is the final piece.** Cloudflare Tunnel gives external access without exposing your home IP or opening ports. A cloudflared pod opens an outbound connection to Cloudflare's network. Requests come back through that tunnel. You get HTTPS automatically, no certificate management on your end. Tailscale provides a private alternative. If you want secure access to something without exposing it to the internet, Tailscale creates an encrypted overlay network that works like a private VPN.

The result is a system where you never SSH into a node to fix something. Everything is defined in Git. Everything is auditable. Everything can be destroyed and rebuilt from the repo in minutes.

## What Runs Here

The cluster isn't empty. I run the things I actually use:

**Linkling** is a bookmark manager for saving and organizing links. Everything I save to read later lives here, synced across devices.

**Audiobookshelf** is a self-hosted audiobook and podcast server. I built this partly because the service exists and partly because it taught me about stateful applications that need persistent storage and proper networking.

**Kube Prometheus Stack** handles monitoring and alerting. Prometheus scrapes metrics from everything running in the cluster. Grafana visualizes those metrics. Alertmanager sends notifications when things go wrong. Before this was in place, I was flying blind.

The applications vary in complexity. But the infrastructure is identical for all of them. Define the resource in YAML, commit to Git, Flux applies it. If something breaks, I can rebuild the entire cluster from the repo and be back to the exact same state.

More projects are coming. More hosted applications are on the way. The infrastructure is solid enough that adding them is now just committing YAML to Git and letting Flux do the work.

## The Things That Broke

I didn't mention failures in that list. But there were plenty, and each one forced me to understand something fundamental.

**Setting up iSCSI with democratic-csi** was harder than I expected. The QNAP NAS has iSCSI LUNs configured, but wiring them into Kubernetes through democratic-csi requires understanding how the CSI driver translates storage requests into actual iSCSI mounts. I misconfigured the initiator settings multiple times. Pods would get stuck in Pending, unable to mount volumes. The error messages were cryptic until I realized I wasn't configuring the CHAP authentication correctly on the QNAP side.

**Permissions errors** plagued me throughout. Containers were trying to write to mounted volumes but getting permission denied. The root cause was that the container user ID didn't match the NAS permissions. I had to learn how to set securityContext in pod specs to run containers with the right UID/GID, and how to configure NFS exports on the QNAP for the right permissions. It sounds simple until you're debugging why a deployment that should work is silently failing.

**Understanding operators** was a conceptual gap. I deployed Kube Prometheus Stack and didn't understand why Prometheus wasn't collecting metrics. It wasn't a networking issue or a configuration issue. It was that operators work differently from standard Kubernetes deployments. An operator watches custom resources (CRs) and creates standard Kubernetes resources based on them. I was editing ConfigMaps when I should have been editing PrometheusRules. Once I understood that operators are just controllers managing custom resources, everything clicked.

**Prometheus not collecting metrics** happened multiple times. Metrics would stop flowing suddenly. The first time, I thought it was a scrape issue. The second time, I checked the Prometheus targets and discovered they weren't healthy. The actual problem: the ServiceMonitor custom resource wasn't matching any services because the label selectors were wrong. Fixing it was one line, but finding the root cause meant understanding the entire ServiceMonitor → Prometheus reconciliation flow.

Every single one of these failures forced me to dig deeper into how Kubernetes actually works. And that's worth way more than a cluster that "just works."

## What's Next

This cluster isn't finished. It's stable, but every month I learn something that makes me want to refactor.

And that's the point.

The deeper dives are coming. How GitOps with Flux actually works — the moment you delete a resource and watch it come back because Git is the source of truth. How SOPS encrypts secrets in Git and why that's more secure than you'd think. How iSCSI and NFS storage work differently and when to use each one. How Renovate automates image updates without you lifting a finger. How Cloudflare Tunnel gives you HTTPS and external access without opening a single port on your router.

But first you need to see the full picture. This is it.

The gap between learning Kubernetes on Rancher Desktop and running it in production isn't the cluster size. It's the operational mindset. How do you manage state? How do you know what changed? How do you handle failures? How do you keep everything secure?

Those questions don't care if you're running on Raspberry Pis or in AWS. The cluster I built answers them at a scale where I can actually see the failures happen, understand them, and fix them. That's something you can't learn from a tutorial.
