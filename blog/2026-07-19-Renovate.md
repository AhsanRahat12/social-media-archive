# Renovate Made Me Stop Checking Registries. Here's How.

I used to manually check for new container image versions.

Every few days I'd search Docker Hub, check the kube-prometheus-stack releases, scan for security patches. Just in case something important dropped. It felt responsible. It also felt like work I shouldn't be doing.

Then Renovate started doing it for me.

Now I get 3 to 4 pull requests a month. Each one says "hey, there's a new version of this image." I review the diff, merge, and Flux deploys it automatically.

I stopped managing versions. I started responding to updates.

## What Renovate Actually Does

Renovate is a bot that watches container registries and opens pull requests when new versions are available.

That's it. But the simplicity masks something powerful.

Every application in my home lab runs inside a Kubernetes deployment. Every deployment specifies a container image with a tag. Renovate watches those tags for changes. When a new version is published, Renovate opens a pull request bumping the tag in my Git repo.

You review the PR. You merge it. Flux sees the change in Git and redeploys with the new image.

The entire flow is automated. You're not manually bumping versions. You're not forgetting to update something. You're not checking registries at 2 AM.

## The Setup

My renovate.json is minimal:

```json
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "kubernetes": {
    "fileMatch": ["\\.yaml$"]
  }
}
```

That's it. It tells Renovate: "watch all my YAML files for Kubernetes manifests and update container image tags when new versions are available."

Renovate does the rest. It scans my repo, finds every container image reference, checks the registry, and opens a PR if there's something new.

---

## Why Separate PRs Matter

Renovate opens one PR per image. If kube-prometheus-stack updates on Monday and Flux updates on Friday, you get two separate pull requests.

This sounds like it would be annoying. It's actually powerful.

You can review each update independently. You can merge one and hold off on another. You can revert one without reverting everything else.

More importantly: if one update breaks something, you know exactly which image caused it. You roll back that specific PR. Everything else stays running.

---

## The Merge Conflict Reality

Sometimes multiple images update at the same time. Both Renovate PRs touch the same file. You get merge conflicts.

In practice this happens maybe once every couple of weeks for me.

The fix is simple: merge one PR, then merge the other. Git asks you to resolve the conflicts. You pick the newer version for each, commit, and both PRs merge cleanly.

It's friction. But it's friction that buys you certainty. You're seeing what changed. You're making the decision to accept it.

## What Actually Ships

Every Renovate PR looks the same. A deployment manifest with one line changed:

```yaml
spec:
  containers:
  - name: kube-prometheus-stack
    image: registry.k8s.io/prometheus/prometheus:v2.47.1  # before
    # becomes
    image: registry.k8s.io/prometheus/prometheus:v2.48.0  # after
```

That's the entire PR. One image tag bumped.

When you merge it, Flux detects the change immediately. Within the reconciliation interval (usually a minute), new pods spin up with the updated image. Old pods terminate gracefully. Your applications stay running.

## The Trust Question

A lot of people ask: "aren't you nervous merging updates without testing?"

For most applications in my home lab? No.

I'm the only user. If something breaks, I notice immediately. And because everything is in Git, I can revert in seconds.

But there's a bigger reason: I don't have time to manually test every image update. If I wait for perfect test coverage, I never update anything. Security patches languish. Bug fixes don't ship.

Renovate solves this by making updates *low-friction*. The cost of reviewing a diff and merging is low. The cost of getting hacked because you're two versions behind on a security patch is high.

Automated updates + low merge friction = you actually stay current.

## What Renovate Catches

Before Renovate, I never manually checked if new versions existed. I'd update something when it broke. Then I'd scramble to fix it.

Now? Critical security patches get proposed automatically. New versions of dependencies land as PRs. I see them. I understand what changed (the diff is right there). Then I merge.

The shift from "check registries manually" to "respond to automated updates" saves hours every month. More importantly, it means I'm never running ancient versions of anything.

A security advisory drops tomorrow. Renovate will open a PR within minutes. I'll merge within hours.

That's not possible if you're manually checking registries.

---

## The Automation Beyond Renovate

Renovate + Flux is the full picture.

Renovate handles the "is there a new version?" question.

Flux handles the "apply this change to the cluster" question.

Together they mean: new image published → PR opened → merged → deployed, all without you touching kubectl.

You're not writing deployment scripts. You're not SSH'ing into nodes. You're not running manual rolling updates.

You're reviewing pull requests and hitting merge.

That's automation done right. Not "remove the human entirely." But "remove the boring manual parts so the human can focus on decisions."

---

## The Lesson That Stuck

I used to think staying current with dependencies required discipline and constant vigilance. Checking registries. Running tests. Planning deployments.

What actually keeps you current is lowering the friction enough that you *want* to do it.

Renovate does that.

A PR takes 30 seconds to review. Merging is one click. Deploying is automatic. The cost of staying updated becomes so low that you just... stay updated.

That's the power of GitOps + Renovate together. Not just automation. Automation that makes the right thing (staying current) the easy thing (merge a PR).
